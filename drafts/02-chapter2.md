## Chapter 2｜Grok Bot — 方針と Go/No-Go の司令塔

### 2.1 概要

Chapter 1 の三欄でいうと、ここは「方針」の欄の話です。衛生ログを進めていたころ、僕が一番つまずいたのは実装そのものではなかった。写真はいつ必須にするか。閉店後だけか、開店前もか。日次の締めは誰が押すか。答えは頭のどこかにあるのに、チャットへ投げるとすぐカラム名やボタンの話に流れます。決まった気がする。翌朝読むと「作って」だけが残っている。

そこに置いているのが Grok Bot です。方針と Go / No-Go。司令塔、と呼んでいます。実装コードは書かせない。専門家や Cursor の Project に振る。衛生ログでは、写真必須の条件も締め方も、ここで一文にしてから先に出しました。「やるか」「どこまでか」「やらない範囲」が短いメモで残るまで、実装側には触らない。夜に読み返して迷子になる回数が減ったのは、決まったことが短く残るようになったからだと思います。

何でも答えてくれる場所、という意味ではありません。答えてくれる場所が一つだと、判断と実装の境目が溶ける。僕がやっているのは逆です。ここには方針だけを載せる。コードの断片は貼らないし、テーブル設計の相談もボタンの位置も、このスレッドではやらない。固まったら実装は Project に渡す。振る先は案件によって違って、衛生ログ本体なら Cursor の箱、別の専門家がいるならそちらです。司令塔のログに差分が混ざらないことだけが、僕にとっては大事でした。

電子書籍の作業とアプリの案件を同じ司令塔で見ている今も、Go の前に実装を始めない一点は変えていません。新規案件を増やしたくなる日はある。増やす前に Go を取る、と決めておくと夜の自分が楽です。機能一覧を並べるつもりはありません。掴んでいる使い方だけを書きます。

### 2.2 やってみよう

画面を開きます。案件は小さくて構いません。衛生ログなら、「閉店後のチェックで写真を必須にするか」くらいで足ります。Chapter 1 で紙に書いた「方針」の欄がある人は、それを持ってきてください。ない人は、いま決めたいことを一文でメモしておきます。コードの話は書かない。決めることだけです。

Grok Bot のチャットを開きます。新しいスレッドでも、既存の司令塔用でも構いません。僕は案件ごとに方針用の場所を分けていますが、最初は一つで大丈夫です。

[画面プレースホルダ: Grok Bot の新規チャット（または司令塔用スレッド）を開いた画面]
キャプション案: 方針用のスレッドを開く。実装用のチャットと混ぜない。

依頼文は短くします。僕がよく送るのは、だいたい次のような文面です。

「衛生ログで、閉店後の日次チェックに写真必須を入れるか決めたい。実装コードは書かないで。やる／やらない、やるならどこまで、やらない範囲、を短く整理して。最後に Go か No-Go を出して。」

「書かないで」を明示し、決める軸を狭くし、Go / No-Go を求める。長く説明しすぎない方が、返事も短くなります。

[画面プレースホルダ: 上記の方針依頼を入力した送信直前の画面]
キャプション案: 「実装コードは書かないで」と「Go / No-Go」を一文に入れて送る。

返事が返ってきたら、長さを見る。カラム名や API の話が混ざっていたら、依頼がまだ混線しています。僕は「方針だけ。実装は触れないで」と返して、短いメモに戻してもらいます。「閉店後は必須／開店前は任意／今回は通知はやらない」くらいになれば十分です。仕様書はいりません。

Go なら、そのメモを実装側に渡す材料にします。渡す先は次の章の Cursor Projects で、ここではまだ箱を開きません。No-Go なら、やらない理由を一行残して終わります。どちらでもいい。決まった、という状態が残れば成功です。

[画面プレースホルダ: Go（または No-Go）と短い方針メモが返ってきたチャット画面]
キャプション案: 決まったことが短く残っているかだけ見る。コードが混ざっていたら依頼をやり直す。

自分のメモへ一言写しておきます。紙の「方針」欄でもメモアプリでもいい。「Go。閉店後は写真必須。開店前は任意。通知は今回やらない」。日付がなくても、案件名があれば後から追えます。司令塔のスレッドは消さない。あとで「あれ、必須にしたんだっけ」と迷ったときに戻れる場所が一つある。それがこの章のゴールです。

実装の画面はまだ開きません。Go の前に差分を見始めると、また朝の決定が夜の試行錯誤に埋もれます。箱を開くのは次の章です。いまは、方針と Go / No-Go が短い形で残っていれば十分です。
