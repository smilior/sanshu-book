## Chapter 1｜三種の神器の全体像

### 1.1 概要

はじめにで書いた混線を、もう少し手前から見ます。衛生ログを進めていたころ、僕は一つのチャットに全部を載せていました。写真をいつ必須にするか。テーブルはどう切るか。ボタンは右か左か。同じスレッドに並ぶ。朝に決めたつもりが、昼にはカラム名の話に吸い込まれて、夜には「そもそもその画面を出すのか」に戻っている。ログは長い。決まったことは残らない。

足りなかったのは道具の数ではなかった、と今は思います。どこで方針を固めて、どこで実装し、どこで困る条件を先に書いておくか。置き場がなかった。三種の神器と呼んでいるものは、その分け方です。名前は大げさです。やっていることは地味です。

方針と Go / No-Go は **Grok Bot** に置いています。実装コードは書かせない。専門家や Cursor の Project に振る。衛生ログでは、写真必須の条件も日次の締め方も、ここで固めてから先に出しました。「作って」より前に、「やるか」「どこまでか」を短いメモで残す。Go が出るまで実装側には触らない。夜に読み返して迷子になる回数が減ったのは、決まったことが短く残るようになったからだと思います。

実装を渡す箱は **Cursor Projects** です。長い案件をリポ単位で抱えられて、並列にもできる。方針が固まったあとで任せる。司令塔のスレッドに差分を書き始めない。混線していたころは、方針メモのすぐ下に試行錯誤が並んでいて、決定と実験の区別がつかなかった。箱が分かれるだけで、朝の判断が夕方まで残ることが増えました。衛生ログ本体と別件の小さな改善を同じ頭で抱えないためにも助かっています。一つの箱に全部を詰め込むとまた混線する。何度かやってから覚えました。

検証の置き場には **pstack** を入れています。Cursor のプラグインで、入れ方は `/add-plugin pstack` のあと `/setup-pstack`。細かい設定は Chapter 4 に回します。掴んでいるのは、「動いてから困るより、困る条件を先に書いておく」ための道具、くらいです。衛生ログでも、写真アップロードの失敗を後から直すより、先に検証の置き場を決めておいた方が手戻りが少なかった。完璧なテスト設計ではない。困る場所を先にメモする、という感覚です。

きれいに並べると製品紹介になります。言いたいのは優劣ではない。同じチャットに全部を載せない、ということだけです。方針・実装・検証を混ぜると、また朝の決定が夜の差分に埋もれます。電子書籍の作業とアプリの案件を同じ司令塔で見ている今も、Go 前に実装を始めない一点は変えていません。

### 1.2 やってみよう

画面は開きません。紙でもメモアプリでも、手元にあるもので十分です。いま抱えている案件を一つだけ選んでください。大きいものでなくていい。衛生ログでいうと、「写真必須の条件を固める」くらいの粒度で足ります。

紙を三つの欄に分けます。左から「方針」「実装」「検証」。線は雑で構いません。

まず「方針」の欄に、いま決めたいことだけを書きます。やるかやらないか。どこまでやるか。やらない範囲。衛生ログなら、「閉店後のチェックでは写真必須」「開店前は任意」といった一文です。コードの話は書かない。カラム名も書かない。ボタンの位置も書かない。決めることだけです。書けないなら、まだ方針が固まっていない、という事実が残ります。それも十分です。

次に「実装」の欄へ。方針が固まったあとで触る箱を書きます。リポ名でも、Cursor の Project 名でも、「衛生ログ本体の箱」でもいい。いまは名前がなくて構いません。大事なのは、方針の欄に書いたことを実装の欄に移さないこと。混ぜない練習です。

最後に「検証」。動いてから困りそうな条件を一行で書きます。衛生ログなら、「写真がアップロードできなかったとき、ログは残すか残さないか」。答えはまだ要りません。困る場所を先に書いておく、という感覚です。pstack の設定はこの段階では触りません。置き場の名前だけです。

三欄が埋まったら、一度読み返します。方針の欄に実装の話が混ざっていないか。実装の欄に Go / No-Go が混ざっていないか。検証の欄が「あとで考える」になっていないか。混ざっていたら、線を引き直して移します。完璧である必要はありません。混ぜない、という一点だけ確認します。

この三欄は、このあとの章でも戻ってきます。Grok Bot に渡すのは方針の欄。Cursor Projects に渡すのは実装の欄。pstack で先に書くのは検証の欄。画面の手順はこれから一つずつ見ます。いまは、手元で分けた、という状態があれば十分です。
